# Reference Repo Registry

This file defines how Spark Lab STB should reference related repositories and systems without confusing them with the active build repo.


## Reference libraries

Reference repos and systems may inform STB, but they should not become the active build surface unless explicitly promoted.

| Reference | Role | How to use | Do not use for |
|---|---|---|---|
| Mobstack | Agent doctrine, MOB architecture, agent-as-business-unit patterns | Adapt useful doctrine into STB agent/playbook language | Dumping broad ecosystem strategy into STB |
| Graphify | Knowledge graph, visual workflow, relationship mapping patterns | Inform visual maps and future memory architecture | Adding unrelated graph implementation too early |
| NotebookLM | Reassurance podcast, source-grounded synthesis, audio reflection workflows | Create personalized transition artifacts and podcast prompts | Treating raw podcasts as final doctrine without review |
| GStack | Build/deploy/product scaffolding philosophy | Inform execution sequencing and lightweight productization | Overbuilding app infrastructure before STB validates patterns |
| Build While You Heal | Ascension path after STB | Define graduation criteria and deeper system bridge | Collapsing STB into a full BWYH installation |
| Shopify / Gumroad references | Digital product/storefront surfaces | Shape simple product delivery paths | Turning STB into full store management |
| Flo case study | First living field test | Extract doctrine, trip wires, offer lessons, consent safeguards | Making Flo’s private material public without review |

## Promotion standard

A reference becomes STB material only after it is:

1. summarized,
2. translated,
3. simplified,
4. checked against STB boundaries,
5. placed into the correct STB folder,
6. reviewed before public use.

## Core warning

Do not let reference libraries turn STB into a junk drawer.

Reference material should sharpen the system, not expand the room.
