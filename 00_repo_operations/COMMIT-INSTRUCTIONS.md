# Commit Instructions

Use conventional commits.

## Format

`<type>: <clear action>`

## Preferred types

- `chore` for repo setup, folders, cleanup, and operations.
- `docs` for doctrine, playbooks, markdown, and instructions.
- `feat` for new product assets, workflows, templates, skills, maps, or modules.
- `fix` for corrections to existing content or broken workflows.
- `refactor` for reorganizing without changing meaning.
- `style` for formatting-only changes.
- `test` for validation scripts or QA docs.

## Scope rules

Keep commits small and scoped.

Commit against the active repo: `MajorDream444/SPARK-LAB-STB`.

Do not commit unrelated changes from reference repos.

Reference repos such as Mobstack, Graphify, NotebookLM, GStack, Shopify or Gumroad, and Build While You Heal may inform the work, but their patterns must be adapted into `SPARK-LAB-STB` intentionally.

## Good examples

- `docs: add STB core doctrine`
- `feat: add webinar funnel map`
- `docs: add Business Leak Map draft`
- `feat: add today template for client interface`
- `refactor: simplify continuity evidence schema`
- `chore: initialize visual workflows room`
- `docs: add repo operations rules`

## Avoid vague examples

- updates
- stuff
- final
- misc
- changes
- new files
- work

## Room naming

When useful, name the folder room in the commit message.

Examples:

- `docs: add repo operations reference registry`
- `feat: add visual workflows platform map`
- `docs: add webinar OS facilitator script`
- `feat: add Gumroad First Doorway Kit outline`

## Final check before commit

Ask:

1. Does this belong in `SPARK-LAB-STB`?
2. Does this support selling, delivering, explaining, or operating STB?
3. Is this in the correct folder room?
4. Does this reduce complexity or create unnecessary clutter?
5. Is the commit message specific enough to understand later?
